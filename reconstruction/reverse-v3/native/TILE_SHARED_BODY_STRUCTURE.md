# The tile drawing shared body (`0x00a22d70`) is a real dispatch

R3 classified 59 of the 121 tile-content values as `shared-body`: their switch case
targets this address instead of assigning a draw image immediately. "Shared body" is
a *classification*, not an explanation, so this tool decodes what the body does.
Generated by `tools/extract_tile_shared_body.py` from the same pinned ELF.

## Structure (current run)

| element | count |
|---|---:|
| immediate comparisons (`cmp r0, #imm`) | 4 |
| register comparisons (`movw r0, #imm` + `cmp r1, r0`) | 3 |
| distinct constants compared | **6** |
| branches in the scanned range | 4 |
| inline jump table entries at `0x00a22ed0` | 77 |
| ... with distinct targets | 51 |
| helper calls | 3 |
| frame slots touched | 5 |

The six constants compared against the frame slot `[fp,-0x540]` are
**`0xe0`, `0x100`, `0x109`, `0x112`, `0x1e0`, `0x200`**, and `0x112` is compared
**twice** (two `movw`/`cmp` pairs 8 bytes apart) - a duplicated branch, recorded as
observed rather than tidied away.

## Its own dispatch

After the comparisons the body reaches a second switch: an **inline offset table at
`0x00a22ed0`** with 77 entries, indexed by `[fp,-0x1c0][1] - 1` (a byte at offset 1
of a record, minus one), dispatched by `add r2, pc, #4` / `ldr r1, [r1, r2]` /
`add pc, r1, r2`. Every entry is a byte offset from `0x00a22ed0`, and all 77 resolve
into the same code region (51 distinct targets).

## What the 51 branch bodies assign (decoded per slot)

Reading a branch as a bag of `movw` immediates conflates two different things, and
an earlier revision of this table did exactly that: it reported "five values
(0, 2, 3, 109, 129)" as if they were one set. Decoding the stores instead shows the
branches write **three frame slots**:

| slot | meaning | distinct values |
|---|---|---:|
| `[fp,-0x548]` / `[fp,-0x54c]` | a draw pair | **49 distinct** (`0x20`-`0x2ea`) |
| `[fp,-0x558]` | a mode | 3 (`0`, `2`, `3`) |

| element | count |
|---|---:|
| branch bodies writing draw slots | 51 / 51 |
| distinct draw values | 49 |
| branches whose pair is equal | 39 |
| branches whose pair differs | 12 |
| branches setting a mode | 50 (mode `0`: 39, `2`: 8, `3`: 3, unset: 1) |

So the values in the draw slots sit in **the same numeric range the `direct` cases
assign** (`110`, `65`, `196`, ...), which is what resolves the open question from
R23: `109` / `129` are draw values, not modes. `0` / `2` / `3` are the mode.

## The common tail is a third dispatch

Every branch ends with `b 0xa234e0`, and that tail dispatches again on a record byte:
`ldrb r0, [r0,#0xc]; cmp r0, #0x45; bne 0xa23540`. When the byte equals `0x45`, it
**overwrites** the draw pair with `0x6d` and, if `[record+3]` is zero, also writes
`0x6d` into the pair at `[fp,-0x540]`/`[fp,-0x544]` (the animated-offset slots), then
forces mode `2`. Recorded as structure: the tail can override a branch's own choice.

## The arithmetic on the taken path

Read from the instructions rather than guessed: a record address is built with a
**64-byte stride** (`add r3, ip, r3, lsl #6`) and a byte is loaded **at offset 8**,
then `(byte - 127) * constant + [fp,-0x19c]` is stored to `object + 0x20c`; the
result of `bl 0x1c3020` is added to **two** frame slots, `[fp,-0x540]` and
`[fp,-0x544]` - an animated offset pair, which is why these 59 values cannot be
expressed as a constant cell.

Helper calls on the path: `0x1c3d4c`, `0xa30e38`, `0x1c3020`.

## Boundaries

- This is a decode of the instruction stream, not an execution trace: which of the
  six constants a given tile content hits at runtime is not observed here.
- The index byte (`record offset 1`) and the byte at record offset 8 are located;
  what produces them is not part of this artifact.
- The 51 targets are recorded as addresses; naming what each branch draws is the
  next step, not a claim made here.
