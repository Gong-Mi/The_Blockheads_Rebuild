# Extracted record fields vs the repository's own tile header

Two incomplete descriptions of the same 64-byte tile record meet here: the header
(`app/src/main/cpp/original_save_format.h`) and the byte fields the drawing path
actually reads (R32). Generated by `tools/crosscheck_tile_record_header.py`.

## The join

| offset | header name | read at | what the code does |
|---:|---|---|---|
| 1 | `backWallType` | `0x00a22ea8` | the byte minus one indexes the 77-entry jump table |
| 3 | `contentsType` | `0x00a23500` | tested against zero |
| 8 | *(undocumented)* | `0x00a22e00` | `(byte - 127) * constant + [fp,-0x19c]` -> `object + 0x20c` |
| 12 | *(undocumented)* | `0x00a234e4` | compared against `0x45` in the tail |

Documented but not read by this path: `raw[0]` (`type`) and `raw[7]`
(`temperatureScaleByte`).

## What this settles and what it adds

- The 64-byte stride the extraction measured is the header's declared record size - two
  independent sources agreeing.
- The shared body's 77-entry table is indexed by **`backWallType - 1`**, not by the
  tile's own type: the table is the back-wall appearance table. That also explains why
  its domain bound is `0x4c` (76) plus one.
- `contentsType` being "tested against zero" in the tail is a *has-contents* test, which
  is what the tape's override branch is gated on.
- Offsets 8 and 12 are **new**: the drawing path uses a byte at offset 8 in its lighting
  arithmetic and compares offset 12 against `0x45` (69), and neither appears in the
  header. They are recorded as extracted facts, not named.

## Boundaries

- The header is the replacement project's own reconstruction, not original source; a
  wrong name there would propagate. The offsets and the size assertion are what
  corroborate.
- Offset 12's `0x45` is a value the code compares, not a proven field meaning (69 is a
  valid tile content value - a candidate reading recorded in R32).
- No runtime trace.
