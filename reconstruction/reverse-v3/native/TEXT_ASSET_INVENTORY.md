# Text assets: where the game's labels come from

Generated by `tools/audit_text_assets.py`. The question is concrete - can the
replacement load its labels from shipped localization data? - and the answer is
no, with the evidence recorded.

## Counts (current run)

| class | count |
|---|---:|
| shipped localization files | 1 |
| key/value pairs in them | **0** |
| NUL-terminated strings in the pinned binary | 42,357 |
| sentence-like strings (conservative filter) | 413 |
| localization references in the replacement sources | 0 |
| author-authored data files in `assets/gamedata` | 2 |
| `displayName` symbol hits | 1 |
| `itemName` / `itemNameForType` / `nameForItemType` / `localizedString` / `NSLocalizedString` | 0 / 0 / 0 / 0 / 0 |

## The one localization file

`en.lproj/InfoPlist.strings` - 45 bytes, zero key/value pairs, only a
`/* Localized versions of Info.plist keys */` comment. It is an iOS shell
artifact. So there is no localization pipeline to consume: the replacement cannot
switch languages, and every label has to come from elsewhere.

## Where the text actually is

The game text is in the binary's string table (42,357 NUL-terminated strings; 413
pass a deliberately conservative sentence filter: at least 12 characters, a capital
start, sentence punctuation, two or more spaces, and none of `/ \ { } [ ] < > @ |`).
Examples: `A BETTER FASTER KILN.`, `A BRIGHT BLUE GLOW.`, `A CAUSE FOR EXTINCTION.`

That catalogue is a **catalogue**, not a verified UI string list: the filter is a
heuristic and the strings are not tied to the widgets that show them. It is the
raw material for one.

## What is still open

Item display names are not solved here. `displayName` exists as a selector (1 hit),
but no `itemName` / `nameForItemType` symbol exists in the string table, and no
short-word name table was found; the names are most likely produced by
`displayName` methods on the item classes, which is a reverse-engineering item of
its own. Recorded as open rather than filled with a guess.

## Boundaries

- String-table membership is not usage: a sentence in the binary may be dead text.
- The filter rejects strings containing `/` so paths and composed names are
  excluded; some legitimate UI text that contains those characters is excluded too.
- The replacement references no localization API at all today, so every row here
  is unwired.

## Correction (E142, 2026-10-10)

The "What is still open" note above is resolved: item display names are not
produced by `displayName` methods and need no localization data - they are
compiled-in constant CFStrings reached through the `nameForItemType` switch
arms at `0x004db268` (full recovery: `ITEM_DISPLAY_NAMES.md`). The 42,357
string count and the 413-sentence catalogue above remain correct as
catalogues; the miss was in looking for single words among sentence-like
candidates instead of following the lookup code.
