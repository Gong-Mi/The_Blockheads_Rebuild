# Item display names: every source audited

The inventory shows item names, so the replacement needs labels. This is the audit
of where they could come from in the shipped APK - and why the obvious searches
mislead. Generated by `tools/audit_item_display_names.py`.

## Counts (current run)

| source checked | result |
|---|---|
| reference names in the domain | 426 |
| `.strings` localization files | 1 (`en.lproj/InfoPlist.strings`) |
| key/value pairs in them | **0** |
| `GameResources/defaultPrices` entries | 266 |
| fields in those entries | `id`, `old_price`, `price` - **no name field** |
| words probed against the binary | 409 |
| words with a standalone-token hit | 34 |
| hits in a name-list context | 35 |
| hits in an ObjC-symbol context | 0 |
| hits in neither context | 81 |
| a name table in the binary | **0** |
| reference names that exactly match an ObjC class | 18 |
| ... that partially match one | 72 |

## Why the token search alone is wrong

Word-by-word, boundary-aware searches do hit: `Amethyst`, `Ruby`, `Emerald`,
`Jewel`, `Diamond`, `Clay` among them. Read the context and they are not item
names:

- `Litzy, Glitter, Sparkle, Sparkles, Mystic, Dazzle, Gemini, Diamond, Amethyst,
  Ruby, Emerald, Sapphire, Jewel, Luna, Moon, Sabrina, Rainbow` - the blockhead
  **character-name list**;
- `Isaac, Roger, Rodney, Roberto, Jon, Colin, Walter, Clinton, Louis, Clayton,
  Chase, Jack, Jay, Ross, Darren, Maurice, Gerald, Alejandro` - a **first-name
  list** (`Clay` only appears inside `Clayton`);
- `OBJC_METACLASS_$_FreightCar`, `OBJC_IVAR_$_OwnershipSign.widthRadius` - **class
  and ivar symbols**.

A boundary-aware match is necessary but not sufficient: the context has to be read
before a hit means anything. That is why the artifact records the context class of
every hit instead of a boolean.

## The one partial answer: class names

ObjC class names do correspond to a subset of items - 18 exact (`Torch`,
`Blockhead`, `Door`, `Ladder`, `Window`, `Bed`, `Boat`, `FishingRod`, `Sign`,
`Rail`, `TrainStation`, `FreightCar`, ...) and 72 partial matches. That covers
placeable objects, not the 426-entry item domain, so class naming cannot be the
general label source.

## Conclusion

Item display names are **not extractable from this APK**: not from localization,
not from the price data, not from the string table. Two paths remain, and the
choice is a product decision rather than a reverse-engineering one:

1. author the labels - the in-repo reference enum
   (`reference_itemtype_enum.txt`, C+ correlation names) is the best available
   source and already carries a name per id; the display form (spacing the
   camel-case, e.g. `FreightCar` -> "Freight Car") would be a transform of that
   reference, not extracted original text;
2. capture the server's item list at runtime, which is where a client-server game
   would keep the authoritative labels.

## Boundaries

- "Not extractable from the APK" is scoped to the files this tool opens: the
  localization tree, `GameResources/defaultPrices`, and the string table of the
  pinned `libApplication.so`.
- The class-name correspondence is a name match, not a proof that the class *is*
  the display label for that item id.
- No device run and no server capture were performed.
