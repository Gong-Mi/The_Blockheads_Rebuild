# Atlas geometry contract (do the tables' cells fit the shipped PNGs?)

Generated by `tools/verify_atlas_geometry.py`. Every sprite table here records a
cell as `(col, row)` under some grid; this tool recomputes the pixel rectangle for
each recorded cell and checks it against the real dimensions of the shipped
atlas, so a claim that cannot be placed in the file is reported instead of
inherited.

## Counts (current run)

| check | rows | cell px | atlas | violations |
|---|---:|---:|---|---:|
| item sprite map, `formula` domain | 344 | 64 | 2048x1024 | **0** |
| item sprite map, `imageTypeForItemType` domain | 82 | 64 | 2048x1024 | **11** |
| tile cells (inherited 64 px convention) | 68 | 64 | 2048x2048 | 0 |
| font glyph rectangles | 500 | - | declared canvases | 0 outside, 0 duplicate rects |

Shipped atlases: `Items.png` 512x256 (SD) / 2048x1024 (HD), `TileMap.png` 512x512
(SD) / 2048x2048 (HD). The prototype grid is 32 columns x 16 rows x 64 px, which
tiles the HD items atlas exactly (32*64 = 2048, 16*64 = 1024) and the SD one at
16 px - and all 344 formula rows land inside it.

## The correction: the grid was mis-attributed, not the data

An earlier revision of this tool checked the `imageTypeForItemType` domain against
`Items.png` (32x16) and reported 11 violations - cells whose rectangle started past
the 1024 px height (e.g. item 1087, col 7 row 18 -> `y = 1152`; item 1089, col 0
row 21 -> `y = 1344`).

That was **a wrong attribution in the check, not a contradiction in the data**.
Two facts in this repository already say where those cells belong:

- `original_item_image_map.tsv` column names now state it explicitly: the cell is
  `image % 32`, `image // 32` - **derived** from the image id the switch returns,
  not a descriptor field read out of the binary (the old names `col_dataA0` /
  `row_dataA0` read like extracted fields, which they never were);
- `original_item_types.tsv` records `atlas_domain=TileMap:32x32` for the whole item
  domain, and `extract_original_item_types.py` enforces `0 <= image < 1024`, so
  `image // 32 <= 31` - a 32-row page, not a 16-row one.

Checked against its own atlas, every cell fits:

| domain | atlas | grid | rows | violations |
|---|---|---|---:|---:|
| item sprite map, `formula` | Items.png 2048x1024 | 32 x 16 x 64 | 344 | 0 |
| item sprite map, `imageTypeForItemType` | TileMap.png 2048x2048 | 32 x 32 x 64 | 82 | 0 |

Row 31 lands at `y + 64 = 2048`, exactly the TileMap height, so the domain's
largest possible cell is still inside. The lesson is recorded in the artifact
(`checks.items.note`): a geometry violation means nothing until the grid it is
measured against is itself evidenced.

## Why the tile row is a weaker claim

The tile tables record only `(col, row)` - no cell size - so the 64 px used here is
inherited from the item convention (both atlases are square multiples of it, and
the recorded tile cells span col 0..30 / row 0..23, which fits 32x32 cells of
64 px inside 2048x2048 with 0 violations). It is marked as inherited in the JSON
(`checks.tiles.note`), not presented as extracted evidence.

## Fonts

All 500 glyph rectangles sit inside their declared canvases with no duplicate
rectangles (`04b03_16.fnt` declares 256x128 while its PNG is 2048x1024 - the 8x
atlas noted in `FONT_ASSET_TABLES.md`; the metrics stay inside the declared
canvas, so the sampler scales rather than the glyphs overflowing).

## Boundaries

- Only geometry is checked: nothing here says a cell contains the right artwork.
- The tile cell size and the two readings for the 11 items are hypotheses with
  arithmetic, not conclusions.
- The SD/HD pair is checked by dimension only.
