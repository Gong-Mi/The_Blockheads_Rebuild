# The tile record fields the drawing path reads

The drawing path walks 64-byte tile records and reads four byte fields of them. This
table is extracted mechanically from the code windows. Generated by
`tools/extract_tile_record_layout.py`.

## Counts (current run)

| element | value |
|---|---|
| code windows scanned | 2 (shared body, tail) |
| record-field reads found | 4 |
| distinct byte offsets | 4 |
| record stride | 64 bytes (`add r3, ip, r3, lsl #6` at `0x00a22dfc`) |

## Correction: there is one record, reached two ways

An earlier revision of this table concluded that three of the four fields belonged to a
*different* object than the lighting byte. That was wrong, and the fix is in the scan:
`[fp,-0x1c0]` is itself a record pointer - `0x00a1dfc4` stores
`[[fp,-0x198]+8] + index*64` into it - so every read through that slot, and the read
that reaches the array directly, are fields of the **same 64-byte tile record**. The
scan now tracks the pointer slot, so the classification no longer splits one record in
two.

## Fields the drawing path reads (4 verified windows)

| offset | read sites | base | what the code does |
|---:|---:|---|---|
| +1 | 3 | `fp-0x1c0` | `backWallType`: indexes the 77-entry table (after subtracting one) and is compared against 2 and 3 |
| +3 | 1 | `fp-0x1c0` | `contentsType`: tested against zero |
| +5 | **9** | `fp-0x1c0` | read by every direct case body; purpose not characterised |
| +6 | 3 | `fp-0x1c0` | tested against zero in the record-setup window |
| +8 | 1 | `[[fp,-0x198]+8] + index*64` | fed into `(byte - 127) * constant + [fp,-0x19c]` |
| +12 | 1 | `fp-0x1c0` | compared against `0x45` in the tail |

`+6` is read through three sibling pointer slots (`fp-0x1c0`, `fp-0x1c8`, `fp-0x1cc`) -
i.e. the same field of three records (the record pointer is kept per index), which is
why it is the one offset classified as read outside the single-pointer chain.

Offset +5 is the busiest field in the drawing path after the type byte and had never
been catalogued; it is recorded as read at nine sites with no characterised purpose.

## What offset +5 does

All nine read sites share one idiom, and the branch that follows it is decisive:

```
ldrb r1, [r1, #5]        ; byte 5 of the record
cmp  r1, #0
movw r1, #0
movgt r1, #1             ; bool = (byte5 > 0)
cmp  r1, #0
moveq r0, #0             ; if the byte is zero, the mode becomes 0
str  r0, [fp, #-0x554]   ; the mode slot
b    0x00a22d74          ; straight into the shared body
```

So `+5` is a **boolean variant selector**: non-zero keeps mode 2, zero demotes it to 0.
The same case bodies write their draw image into `[fp,-0x540]`/`[fp,-0x544]` and then
fall into the shared body, whose first compare cluster sits at `0x00a22d78` - which is
exactly why the six constants it compares are the leaf images those cases just wrote.
The mode slot here (`[fp,-0x554]`) belongs to the same family as `[fp,-0x558]` seen in
the shared body (values 0/2/3, with 2 forced by the tail when `record+0xc == 0x45`).

Offset +12's compared value `0x45` (69) is a valid tile content value, so "this field
holds a content value" stays a **candidate reading**, not a claim.

## Two decoding traps this scan bakes in

- **Linear disassembly across the inline jump table loses sync.** The table at
  `0x00a22ed0` is data; decoding continues past it into garbage, which is why an
  earlier scan of the whole function found a single field and missed the rest. This
  scan runs over known code windows.
- **capstone prints small offsets without a hex prefix** (`#8`, `#1`, `#3`) and larger
  ones with it (`#0xc`). A pattern requiring `0x` misses exactly the byte fields that
  matter - the first version of this scan did.

## Boundaries

- Four reads in two windows: fields read elsewhere in the function (or in other
  functions) are not covered.
- The purposes are what the surrounding instructions do with the value, not a struct
  definition.
- No runtime trace.
