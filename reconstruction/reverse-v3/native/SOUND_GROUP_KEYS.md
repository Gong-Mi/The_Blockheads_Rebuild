# The sound registry: `grp.*` keys and audio file names (R47)

Generated by `tools/extract_sound_group_keys.py`. This is the answer to "how are the 152
shipped sounds grouped", bounded to what the binary states outright.

## Where it comes from

The string literals of this build are merged into one cstring blob, and `{u32 length, u32
pointer}` descriptors point into it. Walking the blob in order yields interleaved tokens:

```
dig.wav  grp.lime  grp.mine  grp.basalt  place.wav  grp.decorator  razor.wav
grp.baby_shark  grp.campfire  grp.solar  ...  craftWorkbench.wav  sword.wav  punch.wav
```

| quantity | count |
|---|---|
| descriptors matching the shape with a cstring target | 17,209 |
| `grp.*` keys | 117 |
| - of which not a prefix of another key | 85 |
| - of which a strict prefix of another key | 32 |
| audio file-name literals | 130 |
| - present in the shipped asset set | 129 |
| - not in the shipped set | 1 (`bird%d.wav`, a format string) |

## Two caveats that stay attached to the numbers

1. **Being a prefix is a fact; being a fragment is an interpretation.** 32 keys are strict
   prefixes of another key. Some are plainly fragments that cannot stand alone
   (`grp.magn` next to `grp.magnet`, `grp.baby_` next to `grp.baby_shark`, `grp.jaw` next to
   `grp.jaws`), but `grp.ruby` is a prefix of `grp.ruby_chandelier` and still reads like a
   real tier key. The JSON reports the mechanical set and says so; it does not silently
   delete the ambiguous ones.
2. **Adjacency is not membership.** Blob order is the compiler's concatenation of literals,
   which is a hint about source order and nothing more. Saying "`grp.bed` contains
   `sighMale.wav`, `sighFemale.wav`, `yawnMale.wav`, `yawnFemale.wav`" needs the call site
   that passes those names together, which this artifact does not have.

## The one name that is not a file

`bird%d.wav` is a **format string**: the bird sounds are generated as `bird1.wav`,
`bird2.wav`, ... at runtime. That matches the evidence class the asset audits already carry
for format-string references, and it means an asset audit that only looks for exact file
names will under-count the audio domain by that family.

## What this unlocks, and the next step

The registry is exactly what a replacement needs to answer `externalMultiSoundWithKey:` /
`multiSoundWithSounds:`: 117 keys, 130 names, no guessing. What it does not yet answer is
membership - which names belong to which key - and that is blocked on the literal-to-code
channel: for this build, cstring literals are not referenced by absolute address (no
direct pool word matched any probed string VA), so the call sites that would join key to
files have to be reached another way. Recorded in `AUDIO_CALL_SITE_LITERALS` and here rather
than papered over.

## Boundaries

- One build, pinned by `elf_sha256` in the JSON.
- The descriptor walk accepts the `{len, ptr}` shape over the whole file; a descriptor whose
  target is not a cstring section is skipped, and a run with fewer than four printable
  tokens is skipped, so this is a *lower bound* on literal runs, not an inventory of all
  strings.
- "Shipped" means present in `audio_asset_coverage.tsv`; the 1 non-shipped name is reported
  by name.
