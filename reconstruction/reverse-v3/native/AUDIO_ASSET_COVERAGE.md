## Why the extraction changed (a real false positive)

The first version regex-scanned the raw bytes for `[\w]+\.wav`. That produced a
file `_KelpPlant.wav` which does not exist and never did: the bytes come from the
ObjC ivar name `OBJC_IVAR_$_KelpPlant.waveTimer`, where `.wav` is the first four
characters of `.waveTimer`. Extraction now goes through NUL-delimited strings and
every name is graded by `tools/string_evidence.py`; the phantom file is gone and
the full run is unchanged at 138 verbatim names.

The "1 ELF string that ships no file" is now `bird%d.wav` - the format pattern
itself, correctly reported as a string that is not a file rather than as a
missing asset.

## The format-string class

`bird1..bird14.wav` have no verbatim string because the original builds them from
`bird%d.wav`. That pattern is a NUL string in the ELF, so these fourteen are
recorded as `format-string` with the pattern as evidence - stronger than the
earlier stem heuristic, which would also have credited any unrelated identifier
that merely contained the letters `bird`.

## The nine with no evidence

`badPath.wav logs.wav lowbuzz.wav pathGood.wav pathOK.wav snowDig.wav
squeakDown.wav squeakUp.wav womanDie.wav` appear neither verbatim, as a pattern,
nor as a stem in any NUL string. They ship and nothing in the pinned binary names
them: either the name is assembled from data this scan cannot see, or they are
leftovers. Recorded as an observation.

## Boundaries

- Evidence is a byte-string membership test on the ELF, not a call-site analysis:
  a name that only appears in dead data still counts.
- `suffix-composition` (an `%@.wav`-style generic pattern) is deliberately graded
  below `format-string`; for audio no such generic pattern exists, so this class
  is empty here.
- The 9 no-evidence entries are candidates, not proof of dead weight.
- No device run, no audible check.
