# How ObjC sends are linked in this build (a recorded negative result)

The audio wiring needs one thing: "which code sends `soundNamed:`". This is the walk down
that path for one selector, with every step's result recorded - including the four scans
that found nothing, because those are what decide which channel this binary actually uses.
Generated by `tools/probe_objc_send_channel.py`.

## Steps and results

| step | result |
|---|---|
| selector string `soundNamed:` | VA `0xecf8e2`, section `__TEXT,__objc_methname,cstring_literals` |
| its `__objc_selrefs` slot | `0xe7de14` - and the string VA has **exactly one** holder, that slot |
| `__objc_msgrefs` units whose selector field holds the string VA or the slot VA | **0** |
| where the selref slot's own value lives | **only** inside `.rel.dyn` (file `0xb3580`) |
| relocation sections | `.rel.dyn` 148,676 entries, `.rel.plt` 611 entries |

So the chain breaks after the selref slot: the string is referenced once (by its slot), the
slot's address is referenced only by a relocation entry, and no coalesced unit carries
either value in the file.

## The send idiom observed in the target method

`-[MJSoundManager soundNamed:]` at `0x00b88aac` starts like this:

```
ldr r3, [pc, #0x2e8]
add r3, pc, r3          ; r3 = PIC base
ldr lr, [pc, #0x29c]
ldr lr, [lr, r3]        ; lr = table[base]  <- a stub descriptor
...
blx lr                  ; the send goes through that stub
```

i.e. messages are dispatched through a **stub table indexed by the function's PIC base**,
and the stub's selector field is written at load time. That matches the `.rel.dyn` finding
above: the file does not contain the value the send needs, so a static search for "who
loads the stub for `soundNamed:`" has nothing to match against.

## Correction: the link does exist, just not here

An earlier revision of this file concluded "the selector send channel in this build is not
statically linkable". That conclusion was wrong in scope and is retracted here. The send is
`objc_msgSend(receiver, <selref slot address>, args...)` - the slot address *is* the SEL
value - and code reaches that slot through **base-relative pool words** in `.text`
(`pool_word + PIC base 0x105faf4 == slot`), which are plain literals and therefore
matchable. What is empty is only the route this probe walks (the slot value and the
coalesced units). The working route is `tools/find_selector_senders.py`, written up in
`SELECTOR_SENDERS.md`.

## What this rules in and out

- **Ruled out** for this build: resolving a selector's call sites by scanning for the
  string VA, the selref slot, or a msgrefs unit that holds either - all four scans are
  empty, and they are empty for a reason that is visible in the data.
- **Still open**: parsing `.rel.dyn` for entries whose target lands in the stub table
  (148,676 entries to walk, and the stub for a given selector has to be identified by the
  relocation symbol it carries), or observing dispatch at runtime - which on this device
  is blocked twice over (the app runs under HyperOS's binary translator, and it must stay
  in the foreground to keep a world loaded).

The project's own reference describes a `__objc_msgrefs` two-literal channel; that recipe
was derived on a different build and does not transfer here as-is. Recording that is the
point of this artifact: the next attempt should start from `.rel.dyn`, not from the
selref/msgrefs path.

## Boundaries

- One selector (`soundNamed:`), one build.
- "Exactly one holder" is a whole-file word scan, so an unaligned or encoded reference
  would be missed; nothing here claims the value is unreferenced in principle, only that
  no plain word holds it.
- The stub table itself is not identified by address here - only the mechanism is.
