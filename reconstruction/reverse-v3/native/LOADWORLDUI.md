## Boundaries

- **r2 vs ELF**: r2 mis-renders several operand forms inside these bodies (`[sp, segment.NOTE]`, `[sp, section..dynsym]`, pool words as bogus instructions like `addeq r7, sp, r4, asr 6`) and its inline pool comments can be wrong for class/CF-string cells (lwu_21 cell 0x007ecdfc annotated 0xffe2ac9c while the file word is 0xffe2ac8c). Every number quoted here was taken from the raw 4-byte words / ELF (file offset == vaddr) or from the GNU cross-listing; garbled lines were resolved by recomputing the encoded offset from the instruction word; cells whose slot word is 0 were treated as load-time relocations (SDK classes, GOT entries).
- **Block literals**: the flags word 0xC2000000 and the descriptor layout {reserved=0, size=0x18, copy, dispose} are read from the pool/descriptor data; the descriptors carry no signature string, so the blocks' declared types were not recovered.
- **lwu_16 / lwu_17 are roster-trimmed**: their listings stop at the next ObjC IMP (0x008087ec -[state] / 0x0080876c -[hostUserPhoto]) while the printed ARM.exidx end (0x00808828 / 0x008087b0) covers a wider range, so the exidx number is not a usable body bound for these two; the decode uses the trimmed listing (15 / 17 words). lwu_18 has a normal listing bound.
- **lwu_06 ownership**: 'the online-* ivars are not released here' is an observation about this body's instructions, not a claim about the class's lifetime behaviour; cache@12 / cloudInterface@16 / windowInfo@8 may well be non-owned (assign/weak) properties. No decompiler was used, so no source-level ownership attribute is asserted.
- **lwu_31 window**: it ends at the ARM.exidx bound 0x00808828 while the next ObjC IMP in the binary is 0x00809210 `LimeTree -[objectType]`; the intervening ~2.5 KB is other classes'/C++ code and is intentionally not attributed to LoadWorldUI.
- **Grade notes**: lwu_11 and lwu_29 are graded census (structural/send/constant summary plus block walk, not a line-by-line reading of all 3883/2924 words); lwu_30 and the 402-word touch twins are census-lite; the 21 `read` bodies were read in full.
- **lwu_34**: the receiver of the last `setFrame:` in four blocks (0x7f1804, 0x7f1c9c, 0x7f2144, 0x7f3688) is loaded from a spilled slot that the linear register model loses after the intervening pack4 calls, so those four pairs (receiver, address) are inferred from the element slot ladder (hostPvpTitleTextView@116 / hostPvpButton@120 / hostNowButton@124 / the closing rect element) rather than proven by dataflow; the other 21 `setFrame:` receivers are anchored by their OBJC_IVAR pool cell, and 8 of them were additionally confirmed by reading the raw listing windows.
- **lwu_34**: the exact meaning of the WindowInfo float fields is not provable from this body alone — the code compares +4 and +0xc against 415.0/48/160/256/... and multiplies them into frames, consistent with 'screen width/height (or content width/height)', but the struct is only ever consumed, never produced, inside this method (windowInfo@8 is written from the argument at 0x007ee140). Recorded as an open point, not a claim.
- **lwu_34**: the two CFString literals ('YOUR ALIAS:' / 'YOUR NICKNAME:') are selected by a float compare at 0x7f0848 (movmi/movne pick); which UI mode each string belongs to is inferred from the sibling selectors and the hostNickNameTitleTextView@100 receiver, not from a string-to-mode table anywhere in this body.
- **lwu_26**: the two escapes in the LAN arm are applied to the host value and the worldName value; port is passed raw. That is what the register flow shows (escape called on the receiver left in r0 by the immediately preceding objectForKey:), but the exact source-level expression order is inferred from the send order, not decompiler output.
- **lwu_00**: the receiver of the middle send in the text-entry teardown (0x00805a2c, `setDelegate:` with arg 0) is the object returned by textFieldAtIndex:0, read out of the register flow rather than proven (the send at 0x00805a54 is the same selector on textEntryAlertView); the exact composite of the mailto: format arguments is also inferred from the send order.
