# Who references an ObjC selector, and where (R45)

The audio wiring question is "which code plays which sound". `AUDIO_API_SURFACE.md` gives the
API; this gives the **reference sites** - the functions that materialise a given selector -
for the audio entry points, and records the mechanism that makes them findable.

Generated by `tools/find_selector_senders.py --list tools/selector_watchlist.txt`.

## The mechanism (this supersedes the route recorded in OBJC_SEND_CHANNEL.md)

A send in this build is `objc_msgSend(receiver, <selref slot address>, args...)`: the slot
address is used *as* the SEL value, and the slot's content in the file is the selector
cstring VA. Code reaches that slot through a fixed PIC base, so the linker leaves
base-relative literals in `.text`:

```
pool_word + 0x105faf4 == target address
```

with the loading instruction being an `ldr rX, [pc, #k]` aimed at that pool word. Two
independent witnesses of the base inside the code:

| witness | arithmetic | result |
|---|---|---|
| `-[MJSoundManager soundNamed:]` @0x00b88aac | `ldr r3,[pc,#0x2e8]; add r3,pc,r3` | base = 0x105faf4 (matches the base in the listing header) |
| slot for `objectForKey:` inside it | `0xffe27408 + 0x105faf4` | 0xe86efc, in `__DATA,__objc_selrefs`, content -> `"objectForKey:"` |

So a selector's reference sites are found by: **string VA -> selref slot -> pool word
(`slot - base`) -> `ldr` instruction -> enclosing method** (nearest IMP at or below the
loader, from the ObjC method map).

## Reference sites for the audio API

| selector | slot | reference sites |
|---|---|---|
| `soundNamed:` | 0xe7de14 | 1 - `World heartbeatDataRecieved:fromPeer:` |
| `multiSoundNamed:` | - | 8 - `World heartbeatDataRecieved:fromPeer:`, `World update:accurateDT:pinchScale:dragInProgress:`, `World placeWorkbenchOfType:atPos:saveDict:placedByClient:placedByBlockhead:placedByClientName:`, `World tap:` x3, `World doCameraScreenshot` |
| `playAtPosition:` | - | 4 - `World placeWorkbenchOfType:...`, `World tap:` x3 |
| `setSoundVolume:` | - | 1 - `MainMenuOptionsUI soundSlider:` |
| `setMusicVolume:` | - | 1 - `MainMenuOptionsUI musicSlider:` |
| `initWithFile:` | - | 2 - `MJMultiSound initWithFile:`, `MJMultiSound initWithFileNames:` |
| `tap:` | - | 1 - `World tap:` |
| `update:` | none | 0 - no slot holds this string VA |

Read as behaviour: in-game sound triggers sit in **`-[World tap:]`** (three sites each for
`multiSoundNamed:` and `playAtPosition:` - the "player acts on a block, sound plays at that
position" path), plus `placeWorkbenchOfType:` (placing), `update:accurateDT:...` (the world
tick), and `doCameraScreenshot`; volume lives in the options screen
(`MainMenuOptionsUI soundSlider:` / `musicSlider:`); sound objects are constructed in
`MJMultiSound initWithFile:` / `initWithFileNames:`.

`World heartbeatDataRecieved:fromPeer:` showing up as the enclosing method for the
`soundNamed:` site was originally only a nearest-IMP fact. It is now
**settled by the prologue walk-back**: for all 19 loader sites in this table, the nearest
`push {…, lr}`
going back from the loader lands exactly on the method-table imp already named (loader
0x555278 sits at `+0x374` inside `-[World heartbeatDataRecieved:fromPeer:]`, IMP
0x00554f04), so the method map has no hole above these sites. Loader entries in
`selector_senders.json` carry the verification inline (`fn_start`, `fn_start_mode`,
`offset`, `attribution: prologue-verified`); the walk-back is the same instrument as
`tools/probe_live_frame_stack.py`.

## Precision: reference sites vs proven sends

A reference site is a function that materialises the selector; it is reliable and cheap. A
*send* additionally needs the send target to be the dispatcher and the selector argument to
be this slot. This tool's send rule is deliberately conservative - an indirect load
(`ldr rN,[rN]`, the SEL materialisation) followed by a `blx` inside the same linear window -
and it catches only 1 site across this watchlist (`playAtPosition:`). The reason is visible
in the disassembly: apportable spills registers to the stack and re-loads them for the send
(`ldr r1,[sp,#0x30]; ldr r1,[r1] ... ldr r3,[sp,#0x34]; blx r3` at 0x005552bc), so a linear
window is the wrong shape for proving sends in general. Treat the site list as **references**,
and do not read "send" from it.

## Next step, concrete

The multi-sound group files are named by the *caller* of `MJMultiSound initWithFile:` /
`initWithFileNames:` (no cstring sits in those two methods' own pools). So: run this same
tool on `initWithFile:` to get its callers, then read the string argument at each call -
that is where the sound-group tables come from. Same shape for `soundNamed:`'s callers,
which is what the in-game trigger wiring needs.

## Boundaries

- One build (pinned ELF sha256 in the JSON), and the base 0x105faf4 is verified by two
  witnesses above, not assumed.
- "Enclosing method" is the nearest documented IMP at or below the loader; a method missing
  from the map would mislabel the site.
- 8 selectors. `update:` legitimately has no slot (the string VA is not held by any selref
  slot), which is why it reports zero rather than an error.
